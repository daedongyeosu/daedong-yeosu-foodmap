# 자동 수집·Preview 병합 운영 규칙

## 목적

배달앱 수집 결과를 원본 그대로 보존하고, 대동여수음식지도의 기존 가게와 지문으로 대조한 뒤 없는 정보만 Preview에 보완한다. 운영 메인은 검증된 Preview 묶음만 승인 후 반영한다.

## 수집 순서

1. 배달의민족
2. 쿠팡이츠
3. 요기요
4. 먹깨비
5. 땡겨요

앱별 수집기는 주문, 장바구니, 결제 동작을 하지 않는다.

## 배치 상태

- `awaiting_archive`: manifest 등록, ZIP 대기
- `received`: 무결성 및 정책 검사 통과, 원본 보관 완료
- `rejected`: 원본은 보관하되 완료성 또는 정책 검사 실패
- `processing`: 지문 대조 및 데이터 정규화 중
- `review_required`: 가게나 메뉴 대응이 애매해 사람 검토 필요
- `preview_ready`: Preview 반영 준비 완료
- `published`: 승인된 운영 반영 완료

## 가게 지문

자동 확정은 강한 근거가 있을 때만 한다.

1. 사업자등록번호가 같으면 동일 가게 후보로 우선한다.
2. 정규화된 상호명과 도로명/지번 주소가 함께 같으면 동일 가게 후보로 본다.
3. 전화번호는 보조 지문일 뿐 단독 확정 근거로 사용하지 않는다.
4. 상호명만 같거나 주소가 불완전하면 `review_required`로 보낸다.
5. 기존 가게가 없으면 배민 단독 가게 후보를 만들고 네이버지도 연결 후보를 생성한다.

이미 완전 수집된 가게는 목록 첫 화면에서 지문을 확인한 뒤 상세수집을 건너뛴다. 기존 가게라도 메뉴, 사진, 가게정보, 원산지, 최소주문 또는 할인 정보가 비어 있으면 필요한 부분만 수집한다.

## 전화번호 공개 우선순위

1. 땡겨요 또는 먹깨비에서 확인한 실제 가게 전화번호
2. 네이버지도 전화번호
3. 위 값이 모두 없을 때만 배민 전화번호

쿠팡이츠와 요기요의 전화번호는 고객 공개값으로 사용하지 않는다. 배민 전화번호는 내부 후보로 먼저 저장하고 즉시 공개하지 않는다.

## 메뉴·사진 병합

- 메뉴에 사진이 없어도 메뉴명과 가격은 보존한다.
- 쿠팡이츠, 요기요, 먹깨비, 땡겨요에서 같은 메뉴 사진을 찾으면 비어 있는 사진만 채운다.
- 기존 사진을 자동으로 덮어쓰지 않는다.
- 메뉴명·가격·옵션이 애매하면 자동 병합하지 않고 검토 대상으로 남긴다.

## 고객 공개와 내부 보관

고객 공개 후보:

- 최소주문금액
- 가게배달 할인
- 픽업 할인
- 가게정보, 가게소개, 가게알림
- 원산지와 사업자정보 중 공개에 적합한 항목
- 수집시각이 붙은 할인 조건과 적용 기준

내부에만 보관:

- 한집배달
- 알뜰배달
- 위 방식 기준의 배달시간·배달팁·할인
- 공개 우선순위가 낮은 전화번호 후보
- 원문 오류 및 수집 진단자료

배달팁, 할인, 최소주문은 변동값이므로 반드시 출처 앱과 수집시각을 함께 저장한다.

## 지역·카테고리 순회

저장 주소별로 음식배달 메뉴 전체보기의 치킨부터 도시락까지 순회한다. 각 카테고리에서 가게 목록 끝을 확인한 뒤 다음 카테고리로 이동하고, 마지막 도시락이 끝나면 다음 저장 주소로 이동한다. 상세수집 전에 가게 지문을 확인해 이미 완전 수집된 가게는 건너뛴다.

## 배포 원칙

- 모든 자동수집 결과는 Preview에 먼저 쌓는다.
- 자동 정규화·지문 대조·누락 보완 결과와 원본 ZIP을 연결해 추적 가능하게 한다.
- 운영 메인 병합과 배포는 현재 프로젝트의 명시적 승인 규칙을 유지한다.
- 충분한 실제 배치 검증 후 사용자가 승인 규칙 변경을 명시하면 운영 자동화 범위를 다시 정한다.

## 대화 연속성

새 채팅에서도 이 문서와 저장소의 HANDOFF 문서를 기준으로 이어간다. ChatGPT가 새 채팅을 스스로 만들 수는 없으므로, 같은 프로젝트에서 새 채팅을 연 뒤 “자동수집 계속하자”라고 하면 이 문서의 현재 단계부터 재개한다.
